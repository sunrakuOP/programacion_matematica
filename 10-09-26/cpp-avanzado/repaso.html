1 Excepciones (try/catch/throw)

El caso concreto que ya viviste: tu clase Matriz sumando dos matrices de tamaño distinto y devolviendo *this en silencio. Eso es un bug esperando a pasar desapercibido. La forma correcta: throw una excepción — el programa se detiene ahí mismo (o lo atrapa un catch) en vez de seguir con un resultado basura.

excepciones.cppc++
class Matriz {
    int filas, columnas;         // el orden de declaracion importa (ver el warning de abajo)
    std::vector<std::vector<double>> datos;
public:
    Matriz operator+(const Matriz& otra) const {
        if (filas != otra.filas || columnas != otra.columnas) {
            throw std::invalid_argument(
                "Matriz::operator+ -- dimensiones incompatibles: (" +
                std::to_string(filas) + "x" + std::to_string(columnas) + ") vs (" +
                std::to_string(otra.filas) + "x" + std::to_string(otra.columnas) + ")"
            );
        }
        // ... suma normal ...
    }
};

int main() {
    Matriz A(2,2), B(3,3);
    try {
        Matriz C = A + B;
    } catch (const std::invalid_argument& e) {
        std::cout << "excepcion atrapada: " << e.what();
    }
}
Compilado con -Wall -Wextra -pedantic, sin warnings, y corrido
excepcion atrapada correctamente: Matriz::operator+ -- dimensiones incompatibles: (2x2) vs (3x3)
el programa sigue vivo despues del catch -- no crasheo
El primer intento tiró un warning real-Wreorder-ctor: declaré datos antes de filas/columnas en la clase, pero los inicializaba en otro orden en la lista de inicialización. C++ inicializa SIEMPRE en el orden de declaración, sin importar el orden que escribas en la lista — un mismatch entre ambos órdenes es casi seguro un bug latente (usar un miembro antes de que otro lo inicialice). Arreglado reordenando la declaración.
Autoevaluación¿Por qué catch (const invalid_argument& e) usa const y referencia, en vez de recibir la excepción por valor?

2 CMake multi-archivo

Hasta ahora, un archivo, un comando de g++. Un proyecto real (como tu OpenGL, que ya tiene varios .cpp/.h y va a seguir creciendo) necesita CMake: describís QUÉ archivos existen y CÓMO se relacionan, una vez, y CMake genera los comandos de compilación por vos.

CMakeLists.txtcmake
cmake_minimum_required(VERSION 3.20)
project(MatrizProyecto LANGUAGES CXX)
set(CMAKE_CXX_STANDARD 20)

add_library(matriz_lib src/Matriz.cpp)              # compila Matriz.cpp una sola vez
target_include_directories(matriz_lib PUBLIC include)

add_executable(main src/main.cpp)
target_link_libraries(main PRIVATE matriz_lib)       # main usa la libreria de arriba

Estructura real que usé: include/Matriz.h (declaración), src/Matriz.cpp (implementación), src/main.cpp (programa) — separar declaración/implementación en .h/.cpp es lo que permite que main.cpp y tests/test_matriz.cpp (tema 3) compartan la misma clase sin duplicar código.

TEST_CASE("suma de matrices del mismo tamano funciona", "[Matriz]") {
    Matriz A(2,2), B(2,2);

TEST_CASE("suma de matrices de distinto tamano lanza excepcion", "[Matriz]") {
    Matriz A(2,2), B(3,3);

}

4 Row-major vs column-major (C++ vs Fortran)

Ya viste la teoría y la trampa en Ruta al FEM, tema 6.5 — aquí, la MEDICIÓN real del lado de C++: cuánto más lento es recorrer un array 2D en el orden "equivocado" para el lenguaje.

benchmark.cppc++
// C++ guarda por FILAS (row-major) -- este orden es secuencial en memoria:
for (int i = 0; i < N; i++)
    for (int j = 0; j < N; j++)
        sumaFilas += A[i][j];

// este orden salta por toda la memoria:
for (int j = 0; j < N; j++)
    for (int i = 0; i < N; i++)
        sumaColumnas += A[i][j];
Medido de verdad, matriz de 4000×4000, dos corridas
recorrer por filas:    41.28 ms
recorrer por columnas: 71.45 ms   (1.7x mas lento)

recorrer por filas:    27.17 ms
recorrer por columnas: 70.92 ms   (2.6x mas lento)
Casi me engaña el compiladorLa primera versión del benchmark no imprimía la suma acumulada — el compilador, con -O2, se dio cuenta de que ese trabajo "no servía para nada" y BORRÓ los dos loops enteros: los dos tiempos salieron en 0.00 ms. Tuve que forzar el uso real del resultado (imprimirlo) para que el benchmark midiera algo de verdad. Esto es eliminación de código muerto — cualquier benchmark que no use su resultado corre este riesgo.
AutoevaluaciónSi este mismo benchmark estuviera escrito en Fortran, ¿cuál de los dos loops (por filas o por columnas) sería el rápido?

5 Precisión de punto flotante

float (32 bits, ~7 cifras decimales confiables) vs double (64 bits, ~15-16 cifras) — nunca comparar floats con ==, y en solvers iterativos (Ruta al FEM 1.4) el error se ACUMULA con cada operación.

Verificado de verdad
0.1 + 0.2 = 0.30000000000000004441
0.1 + 0.2 == 0.3 ?  false

suma de 0.0001 un millon de veces (deberia dar 100.0):
  float:  99.327309   (error = 0.672691)   <- error GRANDE y visible
  double: 100.0000000022  (error = 2.20e-09)  <- error casi cero

comparacion correcta con epsilon: true

El error de float tras un millón de sumas (0.67, un 0.67% de error) no es un detalle académico — es exactamente la clase de error que en un solver iterativo de FEM con miles de pasos puede volver el resultado inútil. Siempre double en código de ingeniería (ya lo veías en Fortran con real(8), Ruta de Código 6.3).

Autoevaluación¿Cómo se compara correctamente si dos double son "iguales" en la práctica?

7 Interoperabilidad C++/Fortran

La verificación más importante de toda esta página. Un .f90 y un .cpp, compilados por separado con gfortran y g++, enlazados en un solo binario, corriendo de verdad.

rigidez.f90fortran
module rigidez_mod
  use iso_c_binding
  implicit none
contains
  subroutine rigidez_barra_c(E, A, L, k) bind(C, name="rigidez_barra_c")
    real(c_double), intent(in), value :: E, A, L
    real(c_double), intent(out) :: k(2,2)
    k(1,1) =  E*A/L;  k(1,2) = -E*A/L
    k(2,1) = -E*A/L;  k(2,2) =  E*A/L
  end subroutine
end module
principal.cppc++
// extern "C" evita el "name mangling" que C++ le pone a los nombres --
// sin esto, el linker nunca encontraria "rigidez_barra_c"
extern "C" {
    void rigidez_barra_c(double E, double A, double L, double k[2][2]);
}

int main() {
    double k[2][2];
    rigidez_barra_c(200.0e9, 0.001, 2.0, k);
}

8 Lambdas y std::function

Una lambda es una función anónima, definible en el lugar donde se usa — el patrón detrás de un comparador custom de std::sort y de CUALQUIER callback de GLFW (Ruta de Código 5.4).

lambdas.cppc++
sort(v.begin(), v.end(), [](int a, int b) { return a > b; });  // descendente

int contadorClicks = 0;
std::function<void()> alHacerClick = [&contadorClicks]() { contadorClicks++; };  // captura por REFERENCIA

int base = 100;
auto sumador = [base](int x) { return base + x; };   // captura por VALOR -- copia congelada
base = 999;  // esto NO afecta a sumador

12 Move semantics avanzado / perfect forwarding

Ya viste el move constructor básico. El siguiente nivel: una función template que recibe un argumento y lo reenvía a otra función SIN perder si el original era temporal (rvalue) o una variable normal (lvalue) — T&& acá es una "referencia universal", no un rvalue puro, y std::forward preserva la categoría original.

forwarding.cppc++
void procesar(int&)  { std::cout << "lvalue"; }
void procesar(int&&) { std::cout << "rvalue"; }

template<typename T>
void reenviar(T&& arg) {           // referencia universal, NO necesariamente rvalue
    procesar(std::forward<T>(arg));   // preserva si arg llego como lvalue o rvalue
}

int variable = 42;
reenviar(variable);   // arg es lvalue -- forward lo mantiene lvalue
reenviar(100);        // arg es rvalue -- forward lo mantiene rvalue
Salida real
pasando una variable (lvalue):
reenviando con std::forward:
  recibido como lvalue (referencia normal)
pasando un temporal (rvalue):
reenviando con std::forward:
  recibido como rvalue (temporal)
Sin std::forwardSi en reenviar llamaras procesar(arg) directo (sin std::forward), arg SIEMPRE llegaría como lvalue a procesar — incluso cuando el original era un rvalue — porque dentro de la función, arg ya es una variable con nombre (y toda variable con nombre es un lvalue). Ese es el error clásico que std::forward existe para evitar.
Autoevaluación¿Por qué toda variable con nombre dentro de una función es un lvalue, sin importar cómo fue "categorizada" al llegar?

13 constexpr

Una función constexpr puede evaluarse EN TIEMPO DE COMPILACIÓN si todos sus argumentos son conocidos entonces — cero costo en tiempo de ejecución.

constexpr.cppc++
constexpr long factorial(int n) { return n <= 1 ? 1 : n * factorial(n-1); }
static_assert(factorial(5) == 120, "...");  // el COMPILADOR verifica esto, no el programa corriendo
Salida real
factorial(5) calculado EN TIEMPO DE COMPILACION = 120

15 RAII para recursos de OpenGL

Ya dominás la Regla de los 5 (constructor de copia, move, destructor...). El siguiente paso natural: envolver un recurso de GPU (un VBO, una textura, Ruta de Código Fase 5) en una clase RAII — se "crea" al construirse, se libera solo al destruirse, y NO se puede copiar (copiar un ID de buffer de OpenGL no duplica el buffer real en la GPU).

raii_buffer.cppc++
struct RAII_Buffer {
    unsigned int id;
    RAII_Buffer() { id = /* glGenBuffers(1, &id); */ ; }
    ~RAII_Buffer() { /* glDeleteBuffers(1, &id); */ }
    RAII_Buffer(const RAII_Buffer&) = delete;             // no se puede copiar un recurso de GPU
    RAII_Buffer& operator=(const RAII_Buffer&) = delete;
};
Salida real (simulando las llamadas GL con prints)
entrando a un scope con un recurso RAII:
  buffer 42 'creado' (simulado, seria glGenBuffers)
  usando el buffer...
  buffer 42 'liberado' automaticamente (seria glDeleteBuffers)
saliendo del scope -- el buffer ya se libero solo

Sin RAII, tendrías que acordarte de llamar glDeleteBuffers a mano en cada punto de salida de la función (incluyendo returns tempranos y excepciones) — con RAII, es imposible olvidarse: el destructor corre siempre.

Autoevaluación¿Por qué RAII_Buffer(const RAII_Buffer&) = delete; es necesario — qué saldría mal si se permitiera copiar esta clase?
