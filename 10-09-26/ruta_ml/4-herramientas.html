4.2 NumPy: vectorizar en vez de hacer bucles

NumPy es "tu Matriz" hecha por expertos: arrays contiguos de números con operaciones que corren en C/Fortran optimizado por debajo. La regla de oro es no escribir bucles sobre los elementos: escribir la operación sobre el array entero (vectorizar). Dos conceptos:

  • Operaciones elemento a elemento: A + B, A * B (¡es Hadamard, no producto de matrices!), np.exp(A).
  • Producto de matrices: A @ B. Detrás hay una librería BLAS que es lo que tu matmul de 1.7 intenta (mal) imitar.
  • Broadcasting: operar un array con otro de forma distinta, estirando las dimensiones. Por ejemplo, (x - x.mean()) / x.std() estandariza todo el vector sin un bucle (tema 1.4).
numpy_demo.pypython
import time
import numpy as np

n = 120
A = np.random.default_rng(0).random((n, n)); B = np.random.default_rng(1).random((n, n))

def matmul_python(A, B):                                    # el triple bucle, igual que en C++
    n = len(A); C = [[0.0] * n for _ in range(n)]
    for i in range(n):
        for j in range(n):
            s = 0.0
            for k in range(n):
                s += A[i][k] * B[k][j]
            C[i][j] = s
    return C

La, Lb = A.tolist(), B.tolist()
t = time.perf_counter(); C1 = matmul_python(La, Lb); t_py = (time.perf_counter() - t) * 1000
t = time.perf_counter(); C2 = A @ B; t_np = (time.perf_counter() - t) * 1000
print(f"n = {n}:  Python puro = {t_py:.1f} ms   NumPy (A @ B) = {t_np:.3f} ms   mismo resultado = {np.allclose(C1, C2)}")

big = np.random.default_rng(2).random((400, 400))
t = time.perf_counter(); big @ big; t_big = (time.perf_counter() - t) * 1000
print(f"n = 400:  NumPy = {t_big:.2f} ms   (mi C++ con el orden i-k-j: 16 ms)")

x = np.linspace(0, 10, 5)
print("broadcasting:  x =", x, "\n               (x - x.mean()) / x.std() =", np.round((x - x.mean()) / x.std(), 3))
Salida real
n = 120:  Python puro = 164.7 ms   NumPy (A @ B) = 3.269 ms   mismo resultado = True
n = 400:  NumPy = 0.67 ms   (mi C++ con el orden i-k-j: 16 ms)
broadcasting:  x = [ 0.   2.5  5.   7.5 10. ] 
               (x - x.mean()) / x.std() = [-1.414 -0.707  0.     0.707  1.414]
  • Con \(n=120\), el triple bucle en Python puro tarda 165 ms y A @ B tarda 3 ms: unas 50 veces más (la primera llamada incluye algo de arranque, por eso el 3.3 ms; el valor estable es más bajo).
  • Con \(n=400\), NumPy tarda 0.67 ms. Tu C++ de 1.7 en el orden i-k-j tardaba 16 ms. No es que tu C++ sea "lento": es que NumPy llama a una BLAS optimizada de nivel experto, con bloques y varios núcleos. Es el motivo por el que, para producción, se usa una librería y no el bucle propio (4.6).
MediciónTodos los tiempos son de mi Mac (NumPy 2.0.2, con la BLAS que trae el sistema). En tu Windows va a dar números distintos, con otra BLAS. Compará la relación, no el valor absoluto.

4.4 scikit-learn: tu código C++ contra un oráculo

scikit-learn tiene casi todos los algoritmos del bloque 2 con una interfaz uniforme: modelo.fit(X, y), modelo.predict(X), modelo.score(X, y). Se usa para trabajo real, pero acá le damos un uso extra, que es el que más te sirve ahora: como oráculo para verificar tu propio código, igual que usás std::sort para probar tu quicksort.

Hice la prueba con la regresión logística de 2.4. El programa exporta_datos.cpp genera los datos (los mismos de 2.4) y los guarda en CSV; scikit-learn los lee y resuelve el mismo problema sin regularizar:

oraculo.pypython
import numpy as np, pandas as pd
from sklearn.linear_model import LogisticRegression

train = pd.read_csv("train.csv")
test = pd.read_csv("test.csv")

modelo = LogisticRegression(penalty=None, max_iter=1000)    # sin regularizar: el mismo problema que resolvio mi C++
modelo.fit(train[["x1", "x2"]], train["clase"])
w = modelo.coef_[0]
print(f"scikit-learn:     w = ({w[0]:.5g}, {w[1]:.5g})  b = {modelo.intercept_[0]:.5g}  "
      f"exactitud test = {modelo.score(test[['x1', 'x2']], test['clase']):.5g}")
Salida real (C++ y scikit-learn sobre los mismos datos)
C++ (mi codigo):  w = (2.72797, 2.65686)  b = 0.0873799  exactitud test = 0.97
scikit-learn:     w = (3.0015, 2.8987)  b = 0.11804  exactitud test = 0.97

La exactitud coincide (0.97), pero los pesos no: 2.73 contra 3.00. El oráculo acaba de decirte algo que a simple vista no se veía: tu descenso por gradiente no había terminado de converger con 2.000 iteraciones. Lo comprobé subiendo las iteraciones:

pipeline_demo.pypython
import pandas as pd
from sklearn.pipeline import make_pipeline
from sklearn.preprocessing import StandardScaler
from sklearn.neighbors import KNeighborsClassifier
from sklearn.model_selection import cross_val_score

df = pd.read_csv("train.csv")
X, y = df[["x1", "x2"]], df["clase"]

# El StandardScaler vive DENTRO del pipeline: en cada pliegue se ajusta solo con los datos de entrenamiento (sin fuga)
for k in [1, 5, 15, 51]:
    modelo = make_pipeline(StandardScaler(), KNeighborsClassifier(n_neighbors=k))
    puntajes = cross_val_score(modelo, X, y, cv=5)
    print(f"k = {k:2d}:  exactitud 5-fold = {puntajes.mean():.3f} +/- {puntajes.std():.3f}")
Salida real

k = 15:  exactitud 5-fold = 0.972 +/- 0.025
k = 51:  exactitud 5-fold = 0.968 +/- 0.029

Esto es el pipeline y la validación cruzada de 2.12 en seis líneas. Notá que StandardScaler está dentro del pipeline: en cada pliegue se ajusta solo con los datos de entrenamiento, así que no hay fuga. En esos datos, \(k=5\) y \(k=15\) empatan en 0.972.

4.5 PyTorch: tensores y derivación automática de verdad

PyTorch es, en lo esencial, lo que construiste en 3.5, pero industrial: un tipo Tensor (como un array de NumPy) que además recuerda las operaciones que se le hicieron y puede derivar por vos con loss.backward(). Además trae capas (nn.Linear, nn.Conv2d), optimizadores (SGD, Adam) y la posibilidad de correr en GPU.

Así quedaría tu XOR de 3.4 (el código es el esquema estándar de PyTorch; no lo pude ejecutar acá, porque PyTorch no está instalado en esta Mac):

xor_pytorch.pypython
import torch
from torch import nn

X = torch.tensor([[0., 0.], [0., 1.], [1., 0.], [1., 1.]])
y = torch.tensor([[0.], [1.], [1.], [0.]])

torch.manual_seed(1)
red = nn.Sequential(nn.Linear(2, 4), nn.Tanh(), nn.Linear(4, 1), nn.Sigmoid())   # la misma 2-4-1
perdida = nn.BCELoss()
opt = torch.optim.Adam(red.parameters(), lr=0.05)

for epoca in range(2000):
    opt.zero_grad()                  # 1) borrar gradientes viejos
    l = perdida(red(X), y)           # 2) hacia adelante
    l.backward()                     # 3) hacia atras: ESTO es tu autodiff de 3.5
    opt.step()                       # 4) paso del optimizador
print(red(X).detach().round(decimals=3))
Sin ejecutarNo lo ejecuté. Es el patrón estándar y lo escribí con cuidado, pero la verificación te toca a vos: instalá PyTorch (el selector oficial en pytorch.org te da el comando según tu sistema; en Windows con GPU NVIDIA el comando incluye CUDA) y comprobá que las cuatro salidas se acercan a 0, 1, 1, 0. Si algo falla, pasame el error y lo vemos.
  • Las 4 líneas del bucle de entrenamiento son las mismas en casi cualquier red: zero_grad, forward, backward, step.
  • loss.backward() recorre el grafo de cómputo hacia atrás, exactamente como tu backward(f) de 3.5.
  • La GPU acelera mucho el producto de matrices grandes; para el XOR no sirve de nada.

4.6 C++ dentro del ecosistema: Eigen, mlpack y modelos entrenados en Python

No tenés que elegir Python o C++. Un flujo típico profesional: se investiga y entrena en Python y se ejecuta en producción en C++ (por velocidad, memoria, o porque corre dentro de un robot o un sistema embebido). Lo que necesitás saber:

  • Eigen: biblioteca de álgebra lineal de C++, solo cabeceras (no se instala nada: le indicás al compilador dónde están, con -I). Tiene MatrixXd, VectorXd, descomposiciones LU, QR, Cholesky, SVD, autovalores. Guía oficial de inicio: Quick Start Guide (mirror).
  • mlpack: biblioteca de ML en C++ (sitio oficial mlpack.org); según los README de su repositorio, en la serie 4.x se puede usar solo con cabeceras y tiene enlaces a Python, Julia, Go y R.
  • Ejecutar modelos entrenados en Python desde C++: existen LibTorch (la versión C++ de PyTorch) y formatos de intercambio como ONNX con su runtime. No verifiqué los detalles de instalación de estos dos: buscá la documentación vigente antes de empezar.

Eigen está instalado en esta Mac (con Homebrew), así que pude medir la diferencia que importa para tu Matriz:

eigen_demo.cppc++
#include <iostream>
#include <chrono>
#include <Eigen/Dense>

using Eigen::MatrixXd;
using Eigen::VectorXd;

int main() {
    // 1) multiplicacion 400x400
    MatrixXd A = MatrixXd::Random(400, 400), B = MatrixXd::Random(400, 400);
    auto t0 = std::chrono::steady_clock::now();
    MatrixXd C = A * B;
    double ms = std::chrono::duration<double, std::milli>(std::chrono::steady_clock::now() - t0).count();
    std::cout << "A * B (400x400) con Eigen: " << ms << " ms   (C[0,0] = " << C(0, 0) << ")\n\n";

    // 2) minimos cuadrados mal condicionado: polinomio de grado 10, 200 puntos, SIN ruido, coeficientes reales = 1
    const int n = 200, d = 11;
    MatrixXd X(n, d);
    for (int i = 0; i < n; ++i) for (int j = 0; j < d; ++j) X(i, j) = std::pow(i / double(n - 1), j);
    VectorXd w_real = VectorXd::Ones(d), y = X * w_real;

    VectorXd w_normales = (X.transpose() * X).ldlt().solve(X.transpose() * y);   // ecuaciones normales
    VectorXd w_qr = X.colPivHouseholderQr().solve(y);                             // QR directo sobre X
    std::cout << "error relativo del coeficiente recuperado (real: todos 1):\n";
    std::cout << "  ecuaciones normales: " << (w_normales - w_real).norm() / w_real.norm() << "\n";
    std::cout << "  QR:                  " << (w_qr - w_real).norm() / w_real.norm() << "\n";
}
Salida real
A * B (400x400) con Eigen: 8.44625 ms   (C[0,0] = 4.33037)

error relativo del coeficiente recuperado (real: todos 1):
  ecuaciones normales: 0.00108751
  QR:                  5.67936e-11
  • Velocidad: el A * B de 400×400 con Eigen tardó 8.4 ms (con -O2, sin otras banderas de optimización), contra los 16 ms de tu orden i-k-j y los 108 de i-j-k. Con -O3 -march=native baja más.
  • Precisión (lo más interesante): ajusté un polinomio de grado 10 a datos sin ruido cuyos coeficientes reales valen todos 1. Con ecuaciones normales (el método de 1.2) el error relativo es 1.1e-3; con QR es 5.7e-11. Son ocho órdenes de magnitud. Es exactamente lo que anticipé en 1.2: formar \(X^TX\) eleva al cuadrado el número de condición.
RutasCompilé con -I/opt/homebrew/include/eigen3 porque ahí lo dejó Homebrew en mi Mac. En tu Windows (o en WSL) la ruta es otra, depende de cómo lo instales (gestor de paquetes, vcpkg, o simplemente bajar los encabezados). Los 8.4 ms son de mi Mac.

4.7 Experimentos reproducibles y puesta en marcha mínima

Con dos PCs y varios modelos, vas a perder tiempo y confianza si no sabés qué corriste. Un hábito barato que se paga solo:

  • Semilla fija en todo experimento (y anotada).
  • Una carpeta por experimento o una fila por corrida en un experimentos.csv con: fecha, hash del commit (git rev-parse --short HEAD), hiperparámetros y métricas de validación y de prueba.
  • Entorno reproducible: requirements.txt en Python; en C++, CMakeLists.txt con las versiones de las dependencias.
  • Guardar el modelo entrenado en un archivo (pesos en binario o CSV) y poder cargarlo sin reentrenar. Es la diferencia entre un experimento y algo que usás.
  • Scripts antes que notebooks para lo que querés repetir; los notebooks son excelentes para explorar, malos para reproducir.
